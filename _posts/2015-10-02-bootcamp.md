== Session : Enterprise ==

* Attendees: Marek Pola and Zoran Jovanovic.
* Executive Summary
** Google has run an Android for Work (AfW) pilot with chosen customers since November. Google has provided Nexus devices.
** There will be a recommended AfW device list. It will be a subset of devices that meet requirements. CDD section 9.5 required. Details not decided yet.
** AfW will be launched end of February and presented at MWC. Business info to OEMs is going out this week. AfW roll out is a long process, a marathon.
** It’s planned to have separate encryption for private and work profiles, with separate corporate PIN.
** SD card encryption is planned in M, a feature Sony already has.
** Crypto-aware apps are planned which can run when corporate profile is still locked.
** Apps can be pushed silently to AfW device. Un-installation can be done silently.
** Application restrictions (e.g. VPN settings, per app VPN) are defined in the app manifest. EMM gets these restrictions automatically via the Play API.
** Android for Work App (code name “Avenger”) brings AfW to older devices running ICS or later. Avenger is based on Divide bought by Google. Apps using the secure encrypted container need to be modified using Avenger API.
** Google is not doing certification but want to work with OEMs. There are two main certifications: Common Criteria and FIPS 140-2.
** Google is running an education program using tablets where OEMs are invited. Tablet is fully configured using NFC and the cloud – IT admin doesn’t have to touch it to configure it.
** There are no security enhancement in MR1, only usability and bug fixes. OEMs are recommended to ship with MR1.
** Google is looking into Corporate owned single use (COSU) devices. This is basically an improved kiosk mode.

=UICC Carrier Privileges=

* Presenter
** Junda Liu
*** works on “home networks”
*** in his spare time likes reading 3gpp standard
* Agenda
**Motivation & Goals
**Benefits to the ecosystem
**Mechanism & APIs
**Next Steps
**FAQ

Motivation & Goals
* Carrier needs access to special APIs for customizations.
* Forcing the OEM to bundle APK:s 
* Carrier apps to be hosted on Google Play. 
* Carriers needs access to special API:s
** APNs
** Radio configurations
* Network parameters
 
Today:
* Force OEM to use system APIs
* These APIs are often proprietary (partly fixed by @SystemApi)
* Carrier apps needs to be part of system image, priv-app

Issues
* BYOD
* Unable to unbundle carrier specific apps from device
 
Goals:
* Unbundle carrier customizations
* Secure & flexible
* Enable carrier apps to be distributed on Google Play
** Apps only need to be installed when needed
** Works with Play Auto Installs
** Public APIs, part of the SDK
** MVNO support from Day One

Move away from propretiary APIs.

If the app does not have a matching SIM card then the APIs can't be called.

Benefits:
* User
** Fewer permissions, faster updates
* Carrier
** Flexible app deployment and update
** Better BYOD experience
** MVNO support
* OEM
** Less OS modification
** Faster time-to-market and faster updates to new Android version
** Hoping to reduce the TA time also... (not on slides but mentioned)
* Ecosystem
** Less Android fragmentation, faster updates
  
Mechanism & APIs
* Trust the UICC as the authority
** Owned by carriers
** SIM OTA updateable by carriers
** Hard to hack into (relativele)
* Android platform loads certificates from the UICC
* Android provides access to certain APIs only to apps that are signe by the certificates
* APIs are public and no new permissions are required

Rules on UICC:
* Leverage existing standards for access control between apps and applets (on the UICC)
* Rules served through an applet on the UICC with AID A00000015141434C00

=Storage on Android= 

* Presenter: Jeff Sharkey

* State in L
** Emulated storage
** Multi-user storage
** Secondary storage
* Improving in M+
* Guidance

External / shared storage (SD card) (not internal storage [emmc])

State in L
* a) Emulated primary (N5, N6)
** == /sdcard
* b) Physical primary (Android One)
* c) Emulated primary physical secondary (Xoom)

How did we get here?
* Android 1.0 commited to permissionless, case insensitive storage mounted at /sdcard
* In hindsight , it created a "wild west" that was difficult to manage
** user confusion, file clean up, orphaned files etc.
* Once an API ships, we need to support it for a very long time.
 
What is a public API?
* Context.getExternalFilesDir()
* Environment.getExternalStorageDirectory()
* /mnt/foo or /proc/foo is NOT a public API.
** quote: "devs should not be nosing in file system!"
 
Emulated storage:
* Emulated /sdcard using a FUSE daemon
* Original design didn't have a physical card
* Originally built for Xoom, but ironically Xoom ended up with a physical SD card after all
* Over time, extended to support multi-user and synthesized POSIX permissions
* FUSE has penalty - Extra roundtrip to user space and bufferbloat

Built a pure kernel-mode driver:
* Viable and works. When made that transition you are subject to any refactoring that happens you end up having to rebase to upstream kernel.
** FUSE API is stable over long term. Very low maintenance.
* A few tricks to help speed up
* larger reads have neglible overhead
* writing has larger overhead ~10-15%

Multi-user storage:
* Each user needs their own /sdcard
** Used inheritance approach from Linux mount namespaces to give each app a unique view
** When zygote forks, we create a mount namespace and bind-mount the user-specific "SD card" into place.
* vold, netd will not have the same view of /sdcard as apps (they are not forked by zygot), and are not multi-user aware
** equivalent of adb shell

Debugging mount namespaces
* View effective mounts through /proc/[pid]/mountinfo

Secondary Storage.
* Secondary external storage
** Xoom purposefully left it read-only, since we didn't have enough time to build a useful developer APIs
** Long-forgotten until we realized that many partners were shipping devices configured like this!
* Wanted to avoid "wild west" of original SD card
** Added CDD language to keep secondary storage to read-only until we could build a developer API story
** "Device implementations that include multiple external storage paths..."

Goals in K:
* Open up secondary external storage:
** Give users clear picture of app storage usage, i.e. clear accountability = who uses the storage
** Clean up when uninstalled, i.e. avoid the need for manual clean-up
  
* Storage Access Framework
** Define an abstraction layer to let client developers focus on what they do best: create content
** Offer a consistent UX around storing data
** Increase security for enterprise users by only granting access to user-selected files.
* Enable user choice and promote competition

Improving in M+:

* Data sources
** Apps storing private data
** Apps sharing data with other apps
** Media from outside the device
* Data destinations:
** Long-term SD cards slots (phone/tablet)
** Long-term USB mass storage (TV)
** Transient storage (USB OTG)
** Cloud storage

Making long-term media more useful
* 32 GB, 2TB etc is a lot of space
 
Make apps-on-SD easier to understand
* Put both apps and data in the same place
** Currently only the app is moved (because when creating the ext4 container on the SD card size must be known upfront and can't be done for data so data remains on the internal userdata partition)
 
Protect user privacy
* Avoid wide-open filesystems which expose GPS in EXIF, etc
* Enable multi-user and enterprise on physical media

To store both apps and data, we need POSIX permissions and SELinux labels
* ext4 for spinning media
* f2fs for flash media (primary internal storage partition on N9)
 
Need to protect private user data
* Wrap in dm-crypt with encryption key tied to single device
** Migrating apps between two devices with app on SD card violates certain assumptions Android makes so this will not be supported.
* Media sharing through MTP or second partition (one open and one encrypted partition for apps)
 
Process is called "adopting" a storage device (ie. encrypting it or adding second partition to make it part of the device).

Looking to make the OTG Story better.

===  Graphics API evolution  by Jesse Hall ===

====  Introducing Radiance (New GRAPHICS API for Android/Chrome OS) ====

====  Modern ====

* OpenGL’s backward-compatibility is a strength

* But also increasingly a liability
** Long accumulation of redundant features and complexity
** Programming model doesn’t reflect modern GPU architecture
** New features difficult to add in non-convoluted ways

* Radiance reflects modern GPUs and apps
** Tiling/binning architectures
** Buffers accessible to both CPU and GPU
** Job-based multi-threaded rendering and resource streaming

* Provides a path from current to expected hardware

====  Efficient and Explicit ====

* Radiance allows work to be done once and reused
** Unique state combinations translated once, used many times
** CommandBuffers can be reused, with varying data
** Traditional APIs force these translations to be done repeatedly.

* Explicit control of when and where work happens
** Explicitly compile shaders and state
** Explicitly release memory and objects when idle
** Explicitly double buffer and synchronize data updates

* Lower overhead, less variability between devices
** Driver doesn’t resolve and validate state at draw time
** Driver doesn’t track resource in-use status on binding changes
** Driver doesn’t have buffer renaming/ghosting heuristics

====  Developer Friendly ====

* Plan to have tighter specification, strict tests
** Start with only the tolerance we need for current hardware

* LLVM-based shader intermediate representation (LLVM-IR!)
** Shaders compiled offline; single front-end compiler
** shader reflection can be done offline, baked into application
** better target for other languages, enables tools ecosystem

* Extendable with restrictions
** Allow experimentation with new hardware features
** With policies (TBD) to ensure a consistent platform for developers

====  Hardware Requirements ====

* Radiance will support multiple hardware levels
* API version and hardware level are independent
* Two hardware levels planned for first version:
** Corresponding to OpenGLES 3.1 and AEP hardware
** Precise details still TBD

* Android still supports Open GL ES 2.0 devices
** Therefore, Radiance drivers will be optional for now
** Devices with capable hardware encouraged to include drivers
 
* Platform and some Google apps will use Radians
** HWUI, SurfaceFlinger, WebView, Chrome will use it if present
** All will maintain OpenGL ES 2.0 support as long as necessary
** Expect to see some efficiency benefits when using Radians

====  Relationship to OpenGL ES ====

* Radiance is Android’s graphics HAL going forward
** Interface between platform and device driver
** Expect Android-specific code to prefer Radiance 

* OpenGL ES is supported for portability
** Some apps will prefer shared-code portability to older Android and other platforms
** Will continue eveolving OpenGL ES with Khronos for portability

* OpenGL ES will remain a separate driver for now
** Long-term, OpenGL likelty to be a wrapper over Radiance
** But will take time to reach parity with native implementations 

Maybe it is time when 90% of devices/apps use Radians


====  Fundamentals ====

* Objects are not reference counted by API
** App is responsible for following object lifetime rules

* Most objects are non-reentrant
** Device object is the only exception
** App is responsible for serializing access to an object
** Different objects may be accessed concurrency

* Objects are configured, then become immutable
** “Compile”, “AllocateStorage”, etc. lock state and resources
** Compile step is where expensive work happens
** Resource structure becomes immutable, not contents 

====  Device ====

* A Device is the top-level object.

====  Queue ====

* Work is submitted to Queues, ordered with Syncs
* A queue can do graphics, compute, and/or copies
** Can do all three kinds of operations
** Expect some apps to use extra copy Queue for resource streaming 
* Queues execute asynchronously from each other
** Except when constrained by Syncs
** Actual Scheduling and Concurrency will depend on hardware 
* Primary operations:
** radQueueSubmitPasses()
** radQueue{Buffer, Image}()
** radQueueCopy{BufferTiImage,ImageToBuffer}()
** radQueue{Fence, Wait} Sync()

* SubmitPasses is intended to be very lightweight

====  Command Buffers ====

* Reusable Command Buffers hold drawing commands

* Collect commands for execution
** Intent is to do most translation to hardware commands while building the CommandBuffer

* Inherits only a few states from the containing pass:
**  targets, viewport, scissor, bindings, uniforms

* Inherited bindings / uiforms allow parameterization
** Per frame of per-mesh-instance transforms

** Current value of animated material parameters 
* Transient command buffers may only be used once
** Parameter from app when creaing a command buffer enables lower overhead in some drivers

====  Pass ====

* Passes are schedulable units of work (to be submitted to Queues)

* A Pass contains *either* graphics or compute work
** Work represented as a sequence of CommandBuffers
** Bindins set on Pass can be ingerited by CommandBuffers 

* Graphics Pass:
** Single set of color and depth targets for the entire pass
** Pass describes how to initialize and finalize each target
*** Initialize: None, Preserve, Clear
*** Finalize: Discard, Store, Resolve 
** Viewport/scissor state inherited by CommandBuffer
** Goal is that tilers never flush within a Pass

* Not reusable


====  Pipelines ====

* Pipelines are compiled shader+state objects

* Pipeline includes all shaders and relevant state
** Avoids recompiling shaders at draw time

* Pipeline is reusable between objects and frames
** Instead of regeneratingcaching over and over as in OpenGL ES

* Related state is organized into objects
** Grouped by conceptulized
** Objects not needed after Pipeine is compiled

* Shaders are collected into Programs
** Programs can be used within multple Pipelines
** Allows some compilation


==== Bind Groups ====

* BindGroups hold resource binding tables

* layout (group=0, index=0)
** uniform UBO0 {...} ubo0;
***  → located to BindGroup Buffers with handle[63:0], offset[95:64] and length[128:96]
* vertex buffer and so on are also bound to bind groups (vertex state → bindgroup buffers)
* App can use up to four Bind Groups
* layout (attrib=0) in vec4 position;
* layout (group=0) in vec4 position;

* App can use up to four Bind Group
** Expect to be orgaized by frequency

====  Shaders ====

* Apps provide shaders in binary intermediate form
** Simpler representation than human-readable source 
** Subset of LLVM semantics with shader-specific functions 
** Target-independent ABI 

* Radiance bitcode (rbc) is different than LLVM, LLVM version independent
** front end

* Google provides GLSL-to-rbc compiler
** Thirdparties can provide compilers for other languages

* Google provides translator from rbc to LLVM
** Optional for drivers to use; can use teir own private IR instead

glsl-> /glsl2rad0/ -> .il → /llvm2rbc/ → .rbc → rbc2llvm → .il → \llvm2gpu\ → GPU Shader

radverify, rad2glsl will be also provided by Google

* New graphics API for Android and Chrome OS
** Modern design reflecting modern mobile hardware
** Explicit, low-overhead, and multi-threading friendly
** Consistent behavior across architectures eases development 
* Runs on OpenGL ES 3.1-capable hardware
* No commited Android release of schedule
* Will become the foundation of graphics on Android
