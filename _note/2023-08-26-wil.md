My $0.02 having spent some time looking at this..I am interested in to see
what others think

To boot ONIE with secure boot enabled you are going to have to have a
signed ONIE grub image as a minimum - and to do that in the community build
you'd have to put your private key into the ONIE repository and that
probably isn't wise :)

You could sign an ONIE grubx64.efi and do your own special private ONIE
release (not sure how that sits with the community...but it's technically
doable)

If you go this route I don't think the ONIE grub currently has the patches
to support secure boot (assuming you want to use the standard linux efi
shim for also authenticating your kernel because what's the point of secure
boot if you don't do that). You also hit headaches with how you release
that grub executable (do you sign all the modules or do a standalone
grub?). You likely have to mess around with the ONIE updater steps, build
steps etc - not trivial :)

I don't know if these changes are of interest to the rest of the community
as it ultimately leads to a locked down private ONIE and it all seems
somewhat counter-intuitive to me: now nobody can really load on their OS
except for the key owner as they won't have the key to sign images. This
seems to defeat the point of ONIE.

What I think makes sense for customers that are security conscious is:
 - Have UEFI ONIE and a system that has secure boot capability but with
secure boot *disabled*
 - Provide customers with a certificate to load your key into the UEFI
firmware database (you could pre-load on your own hardware if you are a HW
and SW vendor)
 - Provide your ONIE OS installer which installs signed bootloader, kernel
etc to work with secure boot when enabled

With this a customer can then enable secure boot once they have installed
your secure OS and your key. The big downside is I think enabling secure
boot itself is a manual process and requires going into the firmware menu.
I've not found a way to be able to enable it from linux but my experience
in this area is virtually nil though - maybe it's possible? It would be
neat if it's possible but I suspect it wouldn't be by design

Note: the above is my opinion only. I'm also not an expert in this area -
I've just been actively tinkering recently with secure boot to see what it
can do and the email thread grabbed my interest

Mark

PS - FWIW I don't think TPM is a requirement for secure boot - it helps add
a measured boot component to your secure implementation but isn't actively
required. I'm happy to be corrected ;)

Specifically on this bit:
"However, once anything can be booted that is not verified through secure boot,
that gives the ability to bypass/alter the TPM, BIOS, grub, etc., thereby
making the system no longer secure (or at least, the potential for not
being secure).  Sort of makes the whole thing pointless... "

My take is if a customer enables secure boot and then protects their switch
(physically and by password protecting the firmware configuration) then
secure boot is a good way of securing the switch after the fact. It assumes
that the UEFI firmware isn't compromised but covers everything from then
on. Am I missing something?

I did think about this a bit more and can see two options that could work.

Option 1: Nothing new required. The HW is shipped with ONIE available and
if a customer wants to use secure boot with SW that is signed they have to
be aware that they need to enable secure boot in the firmware menu and load
in the key to verify the signatures. It sucks there are manual steps but
that's the price of security.

Option 2: We add some extra bits to ONIE - specifically building the
shim.efi bootloader and signing the shim, grub and kernel with a key of the
builders choosing (presumably local). With this if you have a key you could
then build a "secure ONIE" which you could release yourself (nobody else
could build it). This ONIE would boot on a switch with secure boot enabled
(assuming the key is installed of course).
A vendor which provides both HW and SW could use this to ship a secure
switch with both their software and ONIE. If a customer wants to install an
alternate OS they will have to disable secure boot (or install the
alternate OS key). I guess potentially a HW vendor could also choose to
provide a signing service but I'm going to guess that nobody would be
interested in that.
A truly security aware customer should verify that their key database only
contains the key they require and that secure boot is enabled - so some
manual steps are required anyway which makes me wonder if it's worth the
effort of going this route

Would option 2 be of interest to anyone else? Does it go against the ONIE
community open approach? I know at Lenovo (where I work) that we would
probably use this approach if it was available so if it's of interest I can
put in the effort to make the changes. I'd only want to do it if it was
likely to be useful to others too - I personally don't like the idea of a
locked down ONIE....it feels ethically icky :) I can be convinced otherwise
if it is of general interest and would not be purely selfish.

Thoughts?
Mark

> Option 1: Nothing new required. The HW is shipped with ONIE available and

> be aware that they need to enable secure boot in the firmware menu and load
> in the key to verify the signatures. It sucks there are manual steps but
> that's the price of security.
> 
> Option 2: We add some extra bits to ONIE - specifically building the
> shim.efi bootloader and signing the shim, grub and kernel with a key of the
> builders choosing (presumably local). With this if you have a key you could
> then build a "secure ONIE" which you could release yourself (nobody else
> could build it). This ONIE would boot on a switch with secure boot enabled
> (assuming the key is installed of course).
> A vendor which provides both HW and SW could use this to ship a secure
> switch with both their software and ONIE. If a customer wants to install an
> alternate OS they will have to disable secure boot (or install the
> alternate OS key). I guess potentially a HW vendor could also choose to
> provide a signing service but I'm going to guess that nobody would be
> interested in that.

> contains the key they require and that secure boot is enabled - so some
> manual steps are required anyway which makes me wonder if it's worth the
> effort of going this route
